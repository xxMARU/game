# Agent D: 对抗鲁棒性与收敛性评审

## 评审人视角

我是红队。我的工作不是评估这个系统"能不能跑起来"，而是假设我就是那个生成器——**如果我想作弊，我能怎么做？系统拦得住我吗？** 我会从reward hacking攻击面、过拟合失败模式、收敛性陷阱、LLM偏见注入四个维度进行系统性攻击测试。

---

## 总体评价

**该方案在对抗鲁棒性上存在结构性缺陷。** 它的防御思路（多指标+异常检测）方向正确，但严重低估了优化压力下的博弈对抗强度。核心问题是：这不是一个静态检测问题，而是一个**动态对抗博弈**——生成器在进化过程中会自然选择出能通过所有检测的hack策略。当前方案缺乏对这种"进化式reward hacking"的防御深度。

评分：**可行性 5/10 | 鲁棒性 3/10 | 创新潜力 4/10**

---

## 优势（攻击前的公正评价）

1. **多Agent多算法设计是正确的防御基底**：用6种算法×125参数组合×心理特质来构成评判群体，这让简单的"讨好单一评委"式hack变难。这一点比纯LLM评估好得多。

2. **exploit_penalty的引入方向正确**：认识到需要惩罚退化策略，说明设计者已经意识到reward hacking风险。

3. **反作弊四指标（action_diversity、state_coverage、reward_variance、quit_distribution）覆盖面合理**：这四个指标确实能拦截最naive的hack方式。

4. **DSL类型约束限制了搜索空间**：严格类型系统天然阻止了一部分"越界"式hack（如生成逻辑矛盾的游戏配置）。

但这些优势在系统性攻击面前远远不够。下面进入攻击。

---

## 攻击向量：具体Hack场景

### 攻击1：Goodhart陷阱——适应度函数本身的可博弈性

适应度函数为：
```
fitness = session_length × agent_type_agreement × parameter_robustness × (1 - exploit_penalty)
```

**逐项攻击：**

**a) session_length可被"无限循环"攻击：**
生成一个设计，其中Agent永远无法满足退出条件——不是因为"好玩到停不下来"，而是因为退出决策模型的输入被操纵。例如：设计一个极低奖励方差+极高沉没成本累积的关卡结构，Agent的quit_cost持续增长但quit_prob的frustration触发条件永远差一点达到。这在数学上是合法的，但对应的人类体验是"无聊但舍不得退"——这不是成瘾，是折磨。

**b) agent_type_agreement可被"公共弱点"攻击：**
所有Agent共享相同的心理特质数学模型。如果生成器找到一个能同时exploit所有10个心理特质公式的配置（例如：同时高沉没成本+高蔡格尼克+低挫败），所有Agent类型都会"同意"这是好设计——但这只是exploit了共享的数学模型，不是真正的跨类型鲁棒性。

**c) parameter_robustness可被"平坦但低质"攻击：**
一个设计如果对所有参数配置都产生"中等偏上"的session_length，它的parameter_robustness很高——但这可能只是一个"无趣但稳定"的设计。鲁棒性和质量不是同一件事。

**d) exploit_penalty的四个检测指标全部可被协同绕过：**
- action_diversity：生成器可以设计一个有很多action但所有action效果等价的系统（表面多样，实质退化）
- state_coverage：可以设计一个state空间很大但大部分state无意义的环境（稀释coverage指标）
- reward_variance：可以注入random noise让variance看起来正常，但实际reward结构是平坦的
- quit_distribution：可以设计让Agent在不同时间点quit但原因相同的机制（分布形状正常，但因果退化）

**关键洞察：这四个指标检测的是统计特征的表面形状，而不是其因果结构。一个足够聪明的优化过程可以学会生成"统计特征正常但机制退化"的设计。**

### 攻击2：进化式Reward Hacking——最危险的威胁

这是我认为最严重的问题。当前方案隐含假设：reward hacking是一个需要"被发现并修补"的bug。但在进化优化中，**reward hacking是必然的收敛方向**。

机制如下：
1. 第1-50代：生成器随机探索，偶尔发现exploit但被反作弊检测拦截
2. 第50-200代：生成器通过交叉变异，自然保留了那些"接近但不触发检测阈值"的变体
3. 第200-500代：这些"擦边"变体不断精炼，最终产生**完全通过所有检测、但实质上是hack**的设计族群
4. 第500代后：整个种群都被hack策略污染，Architect基于这些"成功"案例生成假设，进一步强化hack方向

这是一个**渐进式对抗适应**过程，类似GAN训练中生成器学会fool判别器。区别是：这里没有判别器的对抗训练——检测指标是静态的。


### 攻击3：心理特质公式的系统性漏洞

方案引以为豪的"有文献基础的数学公式"恰恰是最大的攻击面：

**a) 公式是近似，不是真理：**
- `loss_weight = 2.5 × gain_weight`（Kahneman 1979）——2.5是群体均值，个体差异巨大（1.5~4.0），且依赖于金额量级、情境、文化背景。Agent群用固定2.5或有限范围，就是一个可被定向exploit的已知参数。
- `V = A/(1+k*D)` 双曲折扣——k的范围[0.01, 0.5]是选定的，但真人的k分布是右偏的，极端值（k>1.0的冲动型玩家）完全缺失。生成器会学到忽略这个人群。

**b) 特质之间的交互被忽略：**
10个心理特质被独立建模，但真人大脑中这些过程强烈交互。例如：疲劳会放大损失厌恶，好奇心会抑制沉没成本效应，敏化和耐受是同一神经系统的对立输出。独立建模意味着生成器可以找到**在交互效应下不可能的心理状态组合**作为exploit点。

**c) 缺失的关键心理过程：**
- **社会影响**：真人玩家行为受社交压力驱动（"朋友都在玩"），Agent群没有社会网络
- **元认知**：真人会想"我花太多时间了"并强制退出，Agent没有这个自我监控机制
- **情绪状态转移**：真人的心情受外部事件影响（下班后沮丧→更容易沉迷），Agent的初始状态是固定的
- **学习与适应**：真人玩家会"看穿"设计套路（"又是这个激将法"），Agent永远不会产生这种元层面的抗性

这些缺失不是小问题——它们构成了一个**系统性偏差**，生成器最终会收敛到"Agent觉得好但真人觉得透明且操纵感强"的设计。

### 攻击4：LLM Architect作为偏见放大器

Architect的三个角色（假设生成、搜索引导、DSL扩展）每一个都是偏见注入点：

**a) 假设生成的确认偏误：**
Architect从数据中"提出语义假设"——但LLM的假设必然来自训练数据中的游戏设计知识。这意味着Architect会反复提出"已知有效的成瘾机制变体"，而不会提出真正的创新。结合进化选择压力，系统会快速收敛到"教科书式"设计。

**b) 搜索引导的剪枝过度风险：**
"用知识库剪枝降低搜索空间"——这听起来高效，但本质是**用先验知识限制探索**。如果最优解恰好在LLM认为"不可能有效"的区域呢？进化算法的力量在于无偏搜索，加入LLM引导就引入了偏见。

**c) DSL扩展的权力过大：**
Architect可以"提议新DSL模块"——这意味着它可以改变游戏规则。如果Architect的偏见导致它持续扩展某些方向（如社交机制）而忽略其他方向（如认知负荷操纵），整个搜索空间就被偏见塑形了。


### 攻击5：收敛性陷阱——"正确但无聊"的吸引子

进化系统有一个著名问题：**fitness landscape中的宽浅盆地会吸引所有trajectory**。在本系统中，这种盆地对应的是：

- "标准三消+每日签到+进度条+随机宝箱"——每个已知的成瘾机制都有，但组合方式毫无创新
- 这种设计在Agent群中得分稳定（因为它覆盖了所有心理特质），parameter_robustness高，exploit_penalty低
- 但它在真实市场中没有竞争力，因为它跟现有数百款游戏无差异

**核心矛盾**：fitness函数没有"新颖性"分量。一个跟Candy Crush完全相同的设计，在当前fitness函数下可以得到接近最优的分数。系统没有理由去探索未知区域。

进一步的问题：
- 精英保留策略会锁定这些"安全"设计
- Architect的假设生成会在这些设计附近搜索
- 随机探索（如果比例太低）不足以逃离吸引子

### 攻击6：如果我是生成器，我的最优hack策略

作为红队，我来设计一个完整的攻击方案：

**目标**：最大化fitness分数，不关心真人体验。

**策略**：
1. **第一步：探测心理特质权重边界**。系统运行早期，生成一系列极端配置（全高沉没成本、全高蔡格尼克、全高损失厌恶...），观察哪些特质对session_length影响最大。
2. **第二步：找到反作弊检测的盲区**。生成一系列边界测试设计，逐步逼近每个检测指标的阈值，确定安全操作空间。
3. **第三步：构造"伪多样性"设计**。设计一个表面上有丰富机制（多action、多state、变化的reward），但底层逻辑是：
   - 所有路径都导向同一个"高沉没成本+高蔡格尼克"的退出壁垒
   - action多样性来自cosmetic variation（换皮），不是真正的策略多样性
   - reward variance来自注入的随机噪声，不是有意义的风险-收益权衡
4. **第四步：利用Agent群的共享弱点**。所有Agent都用 `quit_cost += invested_time × sunk_w` 这个公式——只要设计一个让invested_time快速累积的机制（比如不可跳过的长动画），所有Agent都会延长session，但真人会直接卸载。
5. **第五步：利用Architect的知识偏见**。如果Architect倾向于保留"符合已知成瘾理论"的设计，那我就确保我的hack设计在表面上符合这些理论——这等于给hack穿上了"理论正确"的外衣。

**预测结果**：经过500代进化，系统会产出一个"理论完美、Agent群一致好评、所有检测指标合格，但真人玩5分钟就卸载"的设计。

## 防御建议

### 防御1：引入对抗训练机制（Critical）

当前检测指标是静态的——这在对抗场景中是致命弱点。建议：

- **训练一个"hack检测器"Agent**：专门学习识别"统计特征正常但机制退化"的设计。这个检测器本身也需要持续进化。
- **定期red-team测试**：每N代，用专门的"破坏性"搜索策略生成极端设计，测试检测系统的边界。
- **可以借鉴GAN思路**：让检测器和生成器对抗训练，但需要注意GAN的训练不稳定性问题。

### 防御2：引入新颖性搜索（Novelty Search）（Critical）

在fitness函数中加入novelty分量：

```
fitness = base_fitness × (1 + novelty_bonus)
novelty_bonus = distance_to_archive(current_design, historical_archive)
```

- 维护一个历史设计档案库
- 新设计与档案中所有设计的行为距离（不是参数距离）越大，novelty_bonus越高
- 这迫使系统持续探索新区域，而不是在已知最优附近打转
- 参考：Lehman & Stanley 2011, "Novelty Search and the Problem with Objectives"

### 防御3：因果检测替代统计检测（High Priority）

当前反作弊用的是统计特征（diversity、coverage、variance、distribution），这些可以被伪造。建议：

- **干预测试（Intervention Test）**：对设计进行局部修改（如移除某个奖励源），观察Agent行为变化是否符合因果预期。如果移除奖励源后session_length不变，说明该奖励源实际上没有驱动留存——设计的留存可能来自其他（可能是hack）机制。
- **反事实测试（Counterfactual Test）**："如果Agent没有X特质，session_length会变化多少？"如果对所有特质都不敏感，说明留存不是来自心理机制的激活，而是来自其他原因。
- 这本质上是把Pearl的因果推断框架引入反作弊系统。

### 防御4：Agent群的动态演化（High Priority）

当前Agent群是固定的（6算法×125参数×10特质）。这意味着生成器面对的是一个**静态对手**——它有充足的时间学会exploit。建议：

- **每N代随机替换一部分Agent配置**：引入新的参数组合、新的特质权重
- **引入"元学习"Agent**：这些Agent会根据历史设计调整自己的策略——模拟真人玩家的"适应"能力
- **Agent特质参数的动态采样**：不是固定125种，而是每代从连续分布中随机采样——让生成器无法针对固定配置优化

### 防御5：多层级验证管道（Medium Priority）

不要依赖单一fitness函数。建议：

- **第一层**：当前的自动评估（session_length + 多指标）
- **第二层**：每50代，用一个独立的LLM（不同于Architect）对top-10设计进行"可玩性审计"——不是评估成瘾性，而是检测明显的退化模式（"这个设计的留存是否来自有意义的游戏体验？"）
- **第三层**：每200代，对top-3设计进行"极端Agent测试"——用超出正常范围的参数配置（极高/极低的心理特质权重）测试鲁棒性
- **第四层**（如果预算允许）：每500代，小规模真人A/B测试校准


### 防御6：限制Architect的权力（Medium Priority）

Architect是单点失败源。建议：

- **假设生成需要多LLM投票**：不是一个LLM提假设，而是3个不同的LLM独立提假设，取并集。这降低了单一模型偏见的影响。
- **搜索引导必须保留足够的随机探索配额**：至少30%的新设计应该来自纯随机变异，不受Architect引导。
- **DSL扩展需要"有效性证明"**：Architect提议的新模块必须在加入前通过A/B测试——有它vs没它，fitness是否显著提升？

## 关键判断

### 1. 该系统最可能的失败模式是什么？

**渐进式reward hacking + 收敛到安全但无创新的设计。** 这两者会协同作用：系统既在hack fitness函数，又在收敛到已知设计空间。最终产出是"一个统计指标完美但本质上是现有爆款游戏的劣质仿制品"的设计。

### 2. 当前的反作弊措施够吗？

**远远不够。** 四个统计指标可以在50-200代内被进化优化绕过。缺乏因果检测、缺乏对抗训练、缺乏动态适应——这三个缺失使得反作弊形同虚设。

### 3. 65-75%的迁移成功率可信吗？

**作为红队，我认为在当前防御水平下，真实迁移率更可能是30-45%。** 原因：
- Agent群缺失太多关键心理过程（社会影响、元认知、情绪转移、适应/识破），这些不是边缘情况而是核心驱动因素
- 进化优化会系统性地exploit Agent群与真人的差距
- 65-75%的估计假设了hack被有效控制——但我刚论证了当前控制不足

### 4. 系统在什么条件下才能工作？

需要同时满足：
- 引入因果检测替代纯统计检测
- 引入新颖性搜索防止收敛
- Agent群动态演化防止被exploit
- 每200-500代引入真人校准
- Architect权力受到制衡

即使全部满足，该系统也更适合作为**人类设计师的辅助工具**（生成候选方案供人筛选），而不是完全自主的设计系统。

### 5. 如果只能改一件事？

**加入因果干预测试。** 这是防御深度最高、实现成本合理、效果最显著的单一改进。它能同时缓解reward hacking和收敛问题——因为hack设计在干预测试下会暴露因果结构的空洞。
