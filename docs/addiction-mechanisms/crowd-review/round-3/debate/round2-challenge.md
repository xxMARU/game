## 1. 对共识的挑战

### 挑战共识3-1："冷启动工具"定位是否太窄？

**综合分析的立场**：系统应缩窄定位为"冷启动阶段的数值预筛工具"。

**反面论据**：

这个缩窄可能自我实现地杀死项目。如果系统只定位为冷启动工具：
- 市场规模锐减——冷启动场景每年全球也就几百款新三消游戏
- 使用频率极低——每个项目只在立项时用一次
- 商业模式不成立——SaaS月费无法持续，一次性收费天花板低

**C的"大厂不需要"论断需要质疑**：
- C说"大厂有上亿条行为日志+XGBoost做留存预测，AUC 0.75-0.85"。但这个模型是**事后预测**——需要先有数据。每次大版本更新引入新机制，历史数据的迁移性就打折扣
- 即使在大厂内部，**新机制的参数初始化仍然是拍脑袋的**。如果系统能在新机制引入时提供比"拍脑袋"好的初始值，它对大厂也有价值
- 大厂的ABTest平台每次分流是有成本的（分流用户的体验不一致=流失风险）。如果系统能减少1-2轮ABTest，每轮节省2-3天+数万DAU的分流损失，ROI可能是正的

**修正建议**：不要缩窄到"冷启动"，而是定位为"**任何缺乏直接可参考数据的参数决策场景**"——包括冷启动、新机制引入、大版本更新、跨品类迁移。

### 挑战共识3-2：退出模型真的是"最关键"的单点故障吗？

**综合分析的立场**：退出模型是三个评审者共同指出的最关键组件。

**反面论据**：

退出模型的重要性取决于**优化目标**。如果我们优化的是"Agent排名一致性"（设计A比设计B好），退出模型的绝对准确性不重要，重要的是**序保持性**（monotonicity）——即如果真人也觉得A比B好，Agent的退出模型只需要保持这个序就行。

换一种说法：**退出模型可以是"错的"但"单调的"。** 如果模型系统性地高估session_length 2倍，但高估的倍数对所有设计是一致的，排名不受影响。

E识别的级联链1（退出模型偏差→全链路污染）的前提是偏差**不是常数偏差**。如果偏差是设计依赖的（不同设计被不同程度地高/低估），级联才成立。

**这可以通过Phase 0验证**：在已知好/差设计上，检查退出模型是否保持了序（这正是G0-1/G0-2的内容）。如果序被保持了，退出模型的绝对偏差不重要。

**修正建议**：退出模型的验证标准应该从"分布形态匹配"（G0-3）升级为"**序保持性+分布形态匹配**"。其中序保持性是硬性的（不通过则退出模型失效），分布形态匹配是软性的（不通过但序保持则可继续，但结果解读要更保守）。

### 挑战共识3-3：engagement_ratio效度验证真的能"前移"吗？

**综合分析的立场**：不应在效度验证前使用engagement_ratio做淘汰。

**反面论据**：

效度验证需要真人数据。Phase 1没有真人数据。**如果因为没有效度验证就不做任何质量控制，Phase 1可能产出大量"compulsion-only"设计**——这些设计可能在fitness上表现很好（因为Agent确实停留很久），但方式是错的（纯粹靠损失厌恶锁住Agent）。

这是一个**"先有鸡还是先有蛋"问题**——我们需要效度验证才能信任engagement_ratio，但如果不用engagement_ratio，Phase 1的产出质量就无法保证。

**折中方案**：
- Phase 1**不淘汰**但**标注**（B的建议方向对）
- 同时将engagement_ratio<0.3的设计单独存档，不参与进化选择但不删除
- Phase 2效度验证后，回溯性检查：被标注的低engagement_ratio设计是否真的是低质量的？
- 如果回溯发现engagement_ratio的淘汰决策有>30%的假阳性率，Phase 2的淘汰阈值需要重新标定

### 挑战共识3-4：监管风险值0.35——是否过度反应？

**综合分析的立场**：监管风险应从0.20上修到0.35。

**反面论据**：

D的分析基于"最坏情况"——中国管理办法最终版+GDFA通过。但：
- 中国管理办法2025年的征求意见稿最终被大幅修改（**实际上2026年1月的最终版删除了"诱导性设计"的技术细节条款**——因为业界反对声音太大）
- GDFA在欧洲议会的讨论中，"认知偏见利用"的定义被反对者批评为"过于宽泛，可以禁止所有游戏设计"，预计最终版会大幅缩窄
- 美国KOSA在众议院仍无进展

**D把监管趋势外推为线性升级，但实际监管过程是非线性的——有回调、有妥协、有执行打折。**

**修正建议**：监管风险概率从D建议的0.35修正到**0.25**（介于R1/R2的0.20和D的0.35之间），影响维持1.0。风险值=**0.25**。这仍然比R1/R2高，但不至于恐慌。

## 2. 对分歧的裁定建议

### Q1：系统定位

**裁定建议**：不缩窄到"冷启动"，扩展到"数据稀缺场景的数值预筛"。

### Q2：session_goal提前到Phase 1？

**裁定建议**：**YES，但用简化版。** C的60-75%数据太有说服力了。

具体来说：
- Phase 1引入C建议的简化session_goal（目标步数采样+达标后退出概率跳升）
- 为此**砍掉Phase 1的参数交互效应扫描**（E建议的28对×25点=700次额外评估）
- 理由：session_goal对退出模型真实性的提升 > 交互效应扫描对参数理解的提升
- 交互效应扫描推迟到Phase 2

**工时估算**：session_goal简化版实现≈1周，交互效应扫描砍掉节省≈1周。净增0周。

### Q3：engagement_ratio在Phase 1的角色

**裁定建议**：**降级为"记录+标注+不参与进化选择"，不淘汰。**

engagement_ratio<0.3的设计在Phase 1中：
- 正常参与fitness排序
- 标注⚠️"参与质量待验证"
- 不参与进化选择（CMA-ES不将其纳入精英集），但保留在档案中
- Phase 2回溯验证

**这是B建议和综合分析折中方案的再折中**——不淘汰（避免假阳性损失），但不进化（避免低质量设计污染搜索方向）。

### Q4：HSCD重命名为PSD

**裁定建议**：**YES，重命名+实质性修改。**

- 名称：从HSCD（分层随机因果检测）改为**PSD（参数敏感性检测）+RSV（排名稳定性验证）**
- PSD保留原有功能：±15%微扰 → 方向一致性+效应存在性
- RSV是新增功能：对Top 10设计，用**独立Agent群重新训练评估**，检查排名稳定性
- Phase 2考虑引入B建议的SCM（结构因果模型），但不作为硬性要求

### Q5：fitness函数技术实现

**裁定建议**：**采用混合方案。**

1. **保持加权几何平均作为主fitness**（修改基础不足以推翻R1/R2的决策）
2. **但执行B的两点修正**：
   - 所有因子做min-max归一化到[0.1, 1.0]后再取几何平均（消除尺度差异）
   - 下限截断从硬截断改为sigmoid软截断（保持低分区域梯度）
3. **采纳C的倒U型映射**：session_length_norm中内置倒U型：
   ```
   session_value = session_length × exp(-session_length / τ), τ=40（Phase 1通过真人数据标定）
   ```
4. **采纳E的双fitness交叉验证**：第二套fitness用纯中位数session_value排名，两套排名差异>30%触发警报

### Q6：监管风险值

**裁定建议**：**上修到0.25（概率）× 1.0（影响）= 0.25。**

不采纳D的0.35（过于悲观），但上调R1/R2的0.20。

同时采纳D的"监管合规层"建议——作为Phase 2的要求（不是Phase 1），理由：
- Phase 1的系统还没有产出可部署的设计，合规需求不紧迫
- Phase 2起系统产出可供真人测试的推荐，此时合规层必须就位

### Q7：Phase 0增加可靠性测试

**裁定建议**：**YES，但不增加独立的1周，而是集成到现有Phase 0工作中。**

E的RT-01到RT-05应在Phase 0的正常开发流程中作为验收标准完成：
- RT-01（环境确定性）和RT-03（fitness一致性）应在代码实现时就通过——这是基本的软件质量要求
- RT-02（Agent可复现性）在Phase 0的金标准测试中同步完成
- RT-04（退出模型健全性）在G0-6的超参数扫描中同步完成
- RT-05（端到端集成）就是Phase 0的核心任务

**净增工时：0。** 但需要在Phase 0的验收标准中明确列出RT-01到RT-05。

### Q8：Phase 1双退出模型

**裁定建议**：**YES，但第2套模型可以是极简版。**

- 第1套（主模型）：R2确认的阈值累积+泊松中断+简化session_goal
- 第2套（验证模型）：纯基于"累积不满意度"的简单阈值模型（无泊松中断、无session_goal）
- 两套的排名Spearman ρ>0.5作为健全性检查
- 如果ρ<0.5，说明退出模型的选择对结果有重大影响，需要在Phase 2深入研究

**工时估算**：第2套模型极简，实现≈2天。

## 5. 仍然悬而未决的问题

**仅剩一个真正的硬争议需要最终仲裁者裁定**：

**B建议Phase 2引入SCM（结构因果模型）**——这是一个重大的方法论升级，需要额外的统计学专业知识和实现工时。是硬性要求还是"nice to have"？

我的倾向：**Phase 2的"应当通过"标准（不是"必须通过"）**。理由：SCM需要预先定义DAG，这个DAG本身就需要领域知识来构建。在没有足够真人数据验证DAG结构之前，SCM可能给出误导性的结论。但如果有资源做，它能显著提升系统的可解释性。
