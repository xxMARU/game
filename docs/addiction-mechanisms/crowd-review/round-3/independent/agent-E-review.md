## 2. 单点故障分析

### 2.1 定义

单点故障（Single Point of Failure, SPOF）：系统中某一个组件的失败会导致整个系统输出无效的点。

### 2.2 识别出的SPOF

**SPOF-1：退出模型**

退出模型是唯一决定session_length的模块。如果退出模型有系统性偏差（比如所有Agent都倾向于过早退出），**所有downstream的指标都会被污染**——fitness值、排名、Go/No-Go标准全部失效。

冗余设计建议：
- 实现**至少2套独立的退出模型**（R1 Phase 2提到了但R2没有在Phase 1中要求）
- **建议Phase 1就引入第2套退出模型**，两套的排名相关性作为健全性检查
- 如果两套模型排名不一致（Spearman ρ<0.5），说明退出模型是当前瓶颈

**SPOF-2：Gymnasium环境封装**

Agent和游戏引擎之间的接口层。如果封装有bug（比如状态向量缺失关键信息、奖励信号被截断），Agent的所有行为都建立在错误的观测基础上。

冗余设计建议：
- 对Gymnasium环境实现**独立的验证器**（检查状态转移的合法性、奖励的一致性）
- 每100步做一次状态快照和一致性检查

**SPOF-3：fitness函数**

所有进化选择压力都通过单一fitness函数传递。如果fitness函数有设计缺陷（如因子尺度不匹配导致某个维度被忽视），进化将朝着错误的方向收敛。

冗余设计建议：
- 实现**2套独立的fitness函数**，一套用于进化选择，一套用于独立验证
- 选择用的fitness（当前的加权几何平均）和验证用的fitness（如纯session_length的中位数排名）如果排名差异过大，触发警报

## 3. 级联失败分析

### 3.1 级联链1：退出模型偏差 → 系统性偏差传播

```
退出模型先验偏差（FM-05）
  → session_length分布形态偏移
    → fitness_v0（Phase 0）测量偏差
      → Go/No-Go标准G0-3（KS检验）可能恰好通过或失败，取决于偏差方向
        → Phase 1的fitness基线建立在偏差数据上
          → CMA-ES优化方向偏移
            → 最终推荐配置优化的是"让Agent退出模型满意"而不是"让真人满意"
```

**链长：6步。终端影响：系统核心价值归零。**

**断链策略**：
- 在链的第2步断：多套退出模型交叉验证（前面SPOF-1的建议）
- 在链的第4步断：G0-6的超参数扫描已经部分覆盖，但建议加强到**54组采样（不是27组）**
- 在链的第6步断：Phase 2的真人校准是最终的断链点，但如果前面没断，Phase 2才发现问题意味着Phase 1的全部工作白费

### 3.2 级联链2：Reward Hacking进化 → 检测失效

```
初始：简单的exploit（Agent找到高奖励循环）
  → PSD检测到（参数微扰无效但分数高）→ 标记并淘汰
    → 进化压力选择"能通过PSD的exploit"
      → 高级exploit：Agent在微扰参数附近学到了不同策略，使得PSD认为"参数有因果效应"
        → exploit_penalty也低（因为action_diversity被表面多样性掩盖）
          → 假高分设计进入Top 10
            → Architect（LLM）基于这些假高分设计生成下一轮候选 → 偏见固化
```

**链长：6步。终端影响：进化方向被劫持。**

**断链策略**：
- 在链的第3步断：每100轮对Top 3设计做**完全独立的Agent群重新训练+评估**（不是在已训练Agent上微扰，而是从零训练新Agent群）。如果新Agent群排名与旧Agent群排名Spearman ρ<0.7，标记为可疑
- 在链的第6步断：Architect只能看到经过验证的设计，未验证的不进入其上下文

### 3.3 级联链3：环境bug → 隐性质量退化

```
游戏引擎边界条件bug（如棋盘在特定消除组合后进入死局）
  → Agent在该状态被迫退出（非正常退出）
    → 退出模型记录这次为"挫败退出"
      → 包含该状态的设计fitness降低
        → 进化压力避开会触发该bug的参数区域
          → 系统"学到了"避开bug区域，但用户不知道
            → 最终推荐在该参数区域有盲区
```

**链长：6步。终端影响：搜索空间被隐性缩小，且不可检测。**

**断链策略**：
- 在链的第1步断：**Gymnasium环境的形式化验证**——证明任何状态转移序列都不会到达死局。对于三消游戏，这可以通过证明"总是存在至少一个合法匹配或可以洗牌"来实现
- 在链的第3步断：退出分类中增加"环境异常退出"类别，与"挫败退出"区分

## 4. 系统可靠性度量建议

### 4.1 引入MTBF（平均故障间隔时间）类比

在这个系统中，"故障"定义为"一轮完整进化迭代产出的Top 5推荐中，至少1个被后续验证证伪"。

目标：MTBF ≥ 10轮迭代（即每10轮才允许出现1次误推荐）。

如何测量：
- Phase 1结束后，回溯性审计：在进化过程的每一轮，Top 5推荐中有多少在后续轮次中被证伪（排名掉出Top 50%）
- 如果MTBF < 5轮，说明系统稳定性不足，需要加强fitness的鲁棒性

### 4.2 引入可用度（Availability）类比

系统可用度 = 产出有效推荐的时间 / 总运行时间

在这个系统中，"不可用"包括：
- CMA-ES陷入局部最优（产出不改善）
- Reward Hacking被检测到需要人工干预
- 环境bug导致某批次评估无效需要重跑

目标可用度：≥ 0.90（即不超过10%的计算资源浪费在无效评估上）。

### 4.3 Phase 0必须新增的可靠性测试

| # | 测试项 | 方法 | 通过标准 |
|---|--------|------|---------|
| RT-01 | 环境确定性 | 相同种子运行10次，比较状态序列 | 完全一致 |
| RT-02 | Agent训练可复现性 | 相同配置×3次训练，比较最终Q值 | 余弦相似度>0.95 |
| RT-03 | fitness计算一致性 | 相同Agent行为数据×2次fitness计算 | 完全一致 |
| RT-04 | 退出模型健全性 | 极端参数测试（0奖励/最大奖励/0难度/最大难度） | 退出行为单调且合理 |
| RT-05 | 端到端集成测试 | 已知好/差设计×完整流水线 | 好/差排序正确 |

## 5. R3独有发现：被忽略的"模式耦合"风险

### 5.1 什么是模式耦合

在复杂系统中，"模式耦合"（mode coupling）指的是系统在不同操作条件下的行为模式之间存在隐性耦合，导致在一个模式下的优化意外恶化另一个模式。

在本系统中：
- **模式1（探索模式）**：CMA-ES的30%随机注入 + novelty_bonus → 鼓励发现新设计
- **模式2（利用模式）**：CMA-ES的70%协方差引导 → 收敛到最优

这两个模式通过**Agent群**耦合：同一批Agent同时评估探索性设计和利用性设计。**如果Agent在评估利用性设计时的经验影响了其评估探索性设计的行为（比如Q值漂移），两个模式之间就产生了污染。**

**建议：每个设计的评估使用独立初始化的Agent，不在设计之间共享Agent状态。** 这在Phase 0的100 Agent规模下不是问题（每个设计独立跑100个Agent），但在Phase 1如果Agent训练时间较长，可能有人倾向于"预训练"Agent然后微调——**这绝对不能做**。
